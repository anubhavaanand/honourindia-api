# Contributing to Honour India

Thanks for helping put India's scientists, doctors, engineers and
mathematicians on the internet's billboards. This guide covers the development
setup, the data conventions, and what a reviewable contribution looks like.

By participating you agree to the [Code of Conduct](CODE_OF_CONDUCT.md).

## Project layout

This is an npm workspaces monorepo:

```
apps/server/       Hono API + static file server (TypeScript, compiled with tsc)
apps/site/         Demo, docs and figure detail pages (plain HTML/CSS/JS)
packages/embed/    Embeddable widget (TypeScript, bundled with esbuild)
data/figures.json  The catalogue of honoured figures
data/images.json   Per-image file, credit and license (generated by the seeder)
scripts/           Data seeding, research, and publishing scripts
```

## Development setup

Requires Node.js 20 or newer.

```bash
npm install        # install all workspaces
npm run build      # build the widget and the server
npm run dev        # build the widget, then serve on http://localhost:3000
npm test           # run the vitest suite
```

Useful focused commands:

```bash
npm run build -w packages/embed   # rebuild only the widget
npm run build -w apps/server      # compile only the server
npm run typecheck -w apps/server  # typecheck the server
npm test -- apps/server           # run only server tests
```

`npm run dev` rebuilds the widget before starting the server. If you change the
widget, rerun `npm run build -w packages/embed` (or restart `npm run dev`) so
`/embed.js` is fresh.

The server reads `PORT` (default `3000`), plus `LOG_LEVEL` and `LOG_FORMAT`
for the logs. See [.env.example](.env.example).

## Code style

- TypeScript strict mode is on for both workspaces; keep it that way.
- Existing code uses two-space indentation, single quotes, no semicolons, and
  `const`/`let` only where reassignment is needed. Prettier encodes this in
  [.prettierrc](.prettierrc).
- Keep the widget dependency-free and small. It is bundled to
  `packages/embed/dist/embed.js`; avoid adding runtime dependencies.
- Public API responses are JSON only and open CORS by design. Preserve the
  cache headers and attribution fields when changing API code.
- Prefer small, focused pull requests with a clear title in conventional-commit
  form (`fix:`, `feat:`, `docs:`, `test:`, `chore:`).

Before opening a pull request, run:

```bash
npm run lint           # eslint, must report no errors
npm run format:check   # prettier, must report nothing to change
```

`npm run lint:fix` and `npm run format` apply the fixes for you. CI runs all
three checks, so a pull request that fails them will not merge.

`npm install` also installs a pre-commit hook (husky + lint-staged) that lints
and formats the files you stage, so the checks usually run before you remember
to run them by hand.

## Tests

Add or update tests for behavior changes:

- `apps/server/src/__tests__` — data helpers, auth, rate limiting
- `packages/embed/src/__tests__` — widget behavior (jsdom)
- `apps/site/__tests__` — demo site glue

Run `npm test` before opening a pull request. If a change is hard to unit test,
describe how you verified it manually in the PR description.

## Suggesting a figure

You can submit new figures for inclusion in the catalogue either via:

1. **API Endpoint**: `POST /api/v1/figures/submit` with JSON body containing `name`, `born`, `field`, `tagline`, `summary`, and `wiki` (and optional `died`, `quote`, `submitterName`, `submitterEmail`). All submissions enter the moderation queue as pending review.
2. **GitHub Issue**: Use the [Figure Suggestion template](.github/ISSUE_TEMPLATE/suggest_figure.yml) to submit recommendations directly through GitHub issues.

## Adding a figure manually

1. Add an entry to `data/figures.json` under `figures`:

   ```json
   {
     "slug": "unique-slug",
     "name": "Full Name",
     "born": 1900,
     "died": 1980,
     "field": "Physics",
     "tagline": "One line a billboard can show.",
     "summary": "Two or three sentences with sources.",
     "quote": null,
     "wiki": "Exact English Wikipedia page title",
     "era": "modern",
     "enduring": false,
     "stillUsed": null
   }
   ```

   `era` must be one of `ancient`, `medieval`, `colonial`, `modern`, `living`.
   `died` is `null` for living figures. `quote` is either `null` or
   `{ "text": "...", "source": "..." }`.

   If the Wikipedia article has no usable free portrait, add
   `"commonsFile": "Exact Commons file name"` (without the `File:` prefix) and
   an `imageNote` explaining that a monogram is shown.

2. Run `npm run seed:images` to download the lead portrait and record its author
   and license in `data/images.json`.

3. Restart the server (the catalogue is loaded at boot) and check the figure
   detail page and a random billboard.

### Licensing rules

- Only freely licensed portraits may be committed or served. The seeder records
  the Commons author and license for each image.
- Do not add fair-use, rights-managed, or all-rights-reserved images. If no free
  portrait exists, leave the figure without an image; the widget renders a
  monogram.
- Facts are not copyrightable, but summaries should be written or paraphrased
  rather than copied. Link the Wikipedia page for readers.
- The widget displays `credit · license`; do not remove that attribution path.

### Data quality checks

```bash
npm run dedup:figures             # writes data/duplicates-report.json (review only)
npm run dedup:figures -- --fix    # merge exact duplicates (same slug or wiki title)
npm run dedup:figures -- --fix --dry-run
```

Review the report before adding figures. Duplicate slugs or duplicate Wikipedia
titles are the most common problems. `--fix` keeps the first record and only
fills fields that are missing from it; it never overwrites a value that is
already present.

## Pull requests

- Base your branch on `main` and keep unrelated changes out.
- Explain what changed, why, and how you tested it.
- Reference the issue number in the PR description (`Closes #123`).
- Do not commit secrets, API keys, or generated `dist/` output.
- One logical change per pull request; a small PR is much easier to review.

## Reporting bugs and security issues

Open a GitHub issue for bugs and data problems, including the URL, the request,
and the expected versus actual behavior. For security vulnerabilities, contact
the maintainers privately rather than opening a public issue.
